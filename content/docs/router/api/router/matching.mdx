The `@cookbook/router/matching` entrypoint exposes the low-level path-matching pipeline.

```ts docs
import {
  flattenRoutes,
  matchRoutes,
  rankRoutes,
} from '@cookbook/router/matching';
```

It works on `NormalizedRoute[]`.

That is the first trap. Matching is not route authoring. It is not full URL resolution. It is the path-candidate layer after route definitions have already been validated and normalized.

Use router methods such as `router.match()` when you need normal application behavior. Use these helpers when you are building diagnostics, tests, visualization, static analysis, or a custom integration.

## Public exports

`@cookbook/router/matching` exports these values:

```text
flattenRoutes
rankRoutes
matchRoutes
```

It does not export named types.

Use route-config types from `@cookbook/router/route-config` when you need to annotate matching state:

```ts
import type {
  MatchedRoute,
  NormalizedRoute,
  RankedRoute,
  RouteMatch,
  ResolvedSlot,
  ResolvedSlots,
} from '@cookbook/router/route-config';
```

## Pipeline

The safe pipeline is:

```ts
import { validateResolvedRouteTree } from '@cookbook/router/route-config';
import {
  flattenRoutes,
  matchRoutes,
  rankRoutes,
} from '@cookbook/router/matching';

const normalized = validateResolvedRouteTree(routes);

const flat = flattenRoutes(normalized);
const ranked = rankRoutes(normalized);
const match = matchRoutes(normalized, '/users/42');
```

`validateResolvedRouteTree()` belongs to `@cookbook/router/route-config`. It validates first, then returns normalized routes.

`normalizeRoutes()` also belongs to `@cookbook/router/route-config`. It derives a normalized tree, but it is not the safe “validate everything” path by itself.

If you feed garbage into matching, matching will not become your validator. It will just make the garbage harder to debug.

## Related route-config helpers

These helpers are commonly used before matching, but they are not exported from `@cookbook/router/matching`:

```ts
import {
  normalizeRoutes,
  validateResolvedRouteTree,
  validateRoutes,
} from '@cookbook/router/route-config';
```

```ts
function normalizeRoutes(
  routes: readonly RouteDefinition[],
  pathOptions?: RouterPathOptions,
): readonly NormalizedRoute[];

function validateRoutes(
  routes: readonly RouteDefinition[],
  pathOptions?: RouterPathOptions,
): void;

function validateResolvedRouteTree(
  routes: readonly RouteDefinition[],
  pathOptions?: RouterPathOptions,
): readonly NormalizedRoute[];
```

Use `validateResolvedRouteTree()` when an integration needs both validation and normalized output.

```ts
const normalized = validateResolvedRouteTree([
    {
      id: 'users',
      path: '/users',
      children: [
        {
          id: 'users.details',
          path: '{id:int}',
        },
      ],
    },
  ] as const);
```

Custom path constraints are not passed to the matching helpers through `pathOptions`.

Register them before matching, or validate/compose routes through APIs that accept `pathConstraints`.

```ts
import { registerPathConstraints } from '@cookbook/router/path';
import { validateResolvedRouteTree } from '@cookbook/router/route-config';

registerPathConstraints({ slug });

const normalized = validateResolvedRouteTree(routes);
```

## `flattenRoutes(routes)`

```ts
function flattenRoutes(
  routes: readonly NormalizedRoute[],
): readonly NormalizedRoute[];
```

Returns a depth-first pre-order list from a normalized primary route tree.

The order is:

1. route;
2. then its children;
3. then each descendant using the same rule.

```ts
import { validateResolvedRouteTree } from '@cookbook/router/route-config';
import { flattenRoutes } from '@cookbook/router/matching';

const normalized = validateResolvedRouteTree([
    {
      id: 'root',
      path: '/',
      children: [
        {
          id: 'home',
          index: true,
        },
        {
          id: 'users',
          path: 'users',
          children: [
            {
              id: 'users.details',
              path: '{id:int}',
            },
          ],
        },
      ],
    },
  ] as const);

const ids = flattenRoutes(normalized).map(
  (route) => route.id,
);
```

Result:

```ts
[
  'root',
  'home',
  'users',
  'users.details',
]
```

The result is cached in a `WeakMap` by the input normalized-array identity.

```ts
flattenRoutes(normalized) === flattenRoutes(normalized);
// true
```

Slot route trees are not traversed as ordinary primary children by this helper. Slot routes are represented under normalized slot configuration.

## `rankRoutes(routes)`

```ts
function rankRoutes(
  routes: readonly NormalizedRoute[],
): readonly RankedRoute[];
```

Returns ranked path candidates.

Pathless routes are excluded from direct candidates because they do not have a `fullPath` to match.

Sorting uses:

1. higher route score;
2. greater full-path segment depth;
3. lower normalization order.

Each result receives a zero-based `rank`.

```ts
import { validateResolvedRouteTree } from '@cookbook/router/route-config';
import { rankRoutes } from '@cookbook/router/matching';

const normalized = validateResolvedRouteTree([
    {
      id: 'users.catch',
      path: '/users/{*path}',
    },
    {
      id: 'users.show',
      path: '/users/{id:int}',
    },
    {
      id: 'users.new',
      path: '/users/new',
    },
  ] as const);

const ranked = rankRoutes(normalized).map(
  (route) => route.id,
);
```

Result:

```ts
[
  'users.new',
  'users.show',
  'users.catch',
]
```

Static paths beat constrained params. Constrained params beat wildcards. Declaration order is only the final tie-breaker.

```ts
const normalized = validateResolvedRouteTree([
    {
      id: 'first',
      path: '/{first}',
    },
    {
      id: 'second',
      path: '/{second}',
    },
  ] as const);

rankRoutes(normalized).map((route) => route.id);
// ['first', 'second']
```

Like `flattenRoutes()`, ranked output is cached by normalized-array identity.

```ts
rankRoutes(normalized) === rankRoutes(normalized);
// true
```

## `matchRoutes(routes, pathname, pathOptions?, options?)`

```ts
function matchRoutes(
  routes: readonly NormalizedRoute[],
  pathname: string,
  pathOptions?: RouterPathOptions,
  options?: {
    readonly routerUrl?: RouterUrlOptions;
    readonly callUrl?: RouterUrlOptions;
    readonly pathConstraints?: RouterPathConstraints;
  },
): RouteMatch<string> | null;
```

Matches a pathname against ranked normalized route candidates.

The first ranked candidate whose path params parse successfully wins.

```ts
import { validateResolvedRouteTree } from '@cookbook/router/route-config';
import { matchRoutes } from '@cookbook/router/matching';

const normalized = validateResolvedRouteTree([
    {
      id: 'users.dynamic',
      path: '/users/{id:int}',
    },
    {
      id: 'users.new',
      path: '/users/new',
    },
  ] as const);

matchRoutes(normalized, '/users/new')?.id;
// 'users.new'

matchRoutes(normalized, '/users/42')?.params;
// { id: 42 }

matchRoutes(normalized, '/users/abc');
// null
```

`matchRoutes()` receives a pathname, not a full URL.

That means the returned match always starts with:

```ts
search: {}
hash: undefined
href: pathname
```

For full URL matching with search and hash parsing, use `router.match()` or the runtime router.

```ts
const match = router.match(
  '/users/42?tab=settings#activity',
);
```

Use `matchRoutes()` when you deliberately want the path layer.

## Matching options

The `options` object can pass URL policy into the path parser.

```ts
matchRoutes(
  normalized,
  '/Files/a%2Fb/c',
  {},
  {
    callUrl: {
      pathMatch: {
        sensitive: true,
        decode: true,
        trailing: false,
        strict: false,
        wildcardFormat: 'array',
      },
    },
  },
);
```

## Branch construction

The matched branch is ordered from root or pathless layout ancestry to leaf.

Each `MatchedRoute` carries only the params visible at that route level.

```ts
const normalized = validateResolvedRouteTree([
    {
      id: 'organizations',
      path:
        '/organizations/{organizationId:regex([0-9a-fA-F-]+)}',
      children: [
        {
          id: 'organizations.users.show',
          path: 'users/{userId:int}',
        },
      ],
    },
  ] as const);

const match = matchRoutes(
  normalized,
  '/organizations/123e4567-e89b-12d3-a456-426614174000/users/7',
);
```

Branch IDs:

```ts
match?.branch.map((entry) => entry.id);
// [
//   'organizations',
//   'organizations.users.show',
// ]
```

Leaf params:

```ts
match?.params;
// {
//   organizationId:
//     '123e4567-e89b-12d3-a456-426614174000',
//   userId: 7,
// }
```

Branch params:

```ts
match?.branch[0]?.params;
// {
//   organizationId:
//     '123e4567-e89b-12d3-a456-426614174000',
// }

match?.branch[1]?.params;
// {
//   organizationId:
//     '123e4567-e89b-12d3-a456-426614174000',
//   userId: 7,
// }
```

Pathless ancestors are restored through `parentId` even though they are never ranked as direct path candidates.

## Static nested paths

Nested child paths with a leading slash are still joined under the parent after normalization.

```ts
const normalized = validateResolvedRouteTree([
    {
      id: 'policies',
      path: '/policies',
      children: [
        {
          id: 'terms-of-service',
          path: '/terms-of-service',
        },
      ],
    },
  ] as const);

matchRoutes(
  normalized,
  '/policies/terms-of-service',
)?.id;
// 'terms-of-service'

matchRoutes(
  normalized,
  '/terms-of-service',
);
// null
```

This is different from modular route composition with `parent`, where absolute child paths are rejected by `defineRouteTree()`.

## Slot resolution

`matchRoutes()` resolves slots for every route in the active branch that owns layout slots.

```ts
const normalized = validateResolvedRouteTree([
    {
      id: 'dashboard',
      path: '/dashboard',
      layout: {
        slots: {
          modal: {
            routes: [
              {
                id: 'dashboard.modal',
                path: 'modal/{id:int}',
              },
            ],
          },
          sidebar: SidebarFallback,
        },
      },
      children: [
        {
          id: 'dashboard.show',
          path: 'show/{id:int}',
        },
      ],
    },
  ] as const);

const match = matchRoutes(
  normalized,
  '/dashboard/show/7',
);
```

The primary branch is:

```ts
match?.branch.map((entry) => entry.id);
// ['dashboard', 'dashboard.show']
```

Slot state is grouped by owner route ID, then slot name:

```ts
match?.slots.dashboard.modal.status;
// 'empty'

match?.slots.dashboard.sidebar.status;
// 'fallback'
```

Status meanings:

| Status      | Meaning                                                        |
| ----------- | -------------------------------------------------------------- |
| `matched`   | A slot route matched the current pathname.                     |
| `fallback`  | No slot route matched, but the slot has fallback view content. |
| `empty`     | No slot route matched and no fallback view exists.             |
| `disabled`  | Slot config is disabled in resolved state.                     |
| `not-found` | Public render-state status for unresolved slot routing.        |

Normal matching from authored slot config currently produces `matched`, `fallback`, or `empty`. `disabled` and `not-found` remain part of the public slot state contract because render integrations must be able to handle them.

## Validation relationship

Matching does not replace validation.

```ts
import {
  normalizeRoutes,
  validateResolvedRouteTree,
  validateRoutes,
} from '@cookbook/router/route-config';
```

```ts
validateRoutes(routes);

const normalized = normalizeRoutes(routes);

const safeNormalized = validateResolvedRouteTree(routes);
```

`validateRoutes()` rejects invalid route identity, duplicate route IDs, duplicate normalized paths, invalid index/pathless/redirect combinations, malformed layouts, malformed slots, malformed intercepts, invalid URL descriptors, unsafe keys, inherited parameter collisions, and invalid PathKit patterns.

`normalizeRoutes()` derives full paths, inherited params, scores, order, slots, and intercept metadata. It can validate path contracts while normalizing, but it is not complete route-tree validation.

`validateResolvedRouteTree()` validates first and then normalizes.

Use that when you do not want the router to be the first thing that finds your bad tree.

## What this API does not do

`matchRoutes()` does not:

* parse `?search`;
* parse `#hash`;
* apply middleware;
* run redirects;
* run rewrites;
* run lifecycle hooks;
* perform call-site interception;
* commit navigation;
* preload route modules;
* start or dispose a router.

It matches a pathname against already-normalized route candidates. Nothing more.

## Where this bites

### Normalized does not mean valid

This is not enough for untrusted or generated input:

```ts
const normalized = normalizeRoutes(routes);
const match = matchRoutes(normalized, '/users/42');
```

Use this instead:

```ts
const normalized = validateResolvedRouteTree(routes);

const match = matchRoutes(normalized, '/users/42');
```

### `matchRoutes()` ignores query strings and hashes

This is wrong:

```ts
matchRoutes(
  normalized,
  '/users/42?tab=settings#activity',
);
```

`matchRoutes()` expects a pathname. Use the runtime router for full hrefs:

```ts
router.match(
  '/users/42?tab=settings#activity',
);
```

### Pathless routes are branch entries, not candidates

A pathless layout can appear in `match.branch`.

It will not appear in `rankRoutes()` because direct candidates need `fullPath`.

That is the point. Layouts wrap routes; they do not compete with them.

### Candidate ranking is deterministic, not forgiving

If two routes have equal specificity, declaration order decides.

Do not rely on “obvious intent.” Put the static route in the tree and let ranking prove it, or use validation/tests to catch ambiguous design.
